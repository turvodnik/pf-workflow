# Процесс pf-workflow: от идеи до ретро

English version: [PROCESS.en.md](PROCESS.en.md)

## 0. Правило масштаба — когда конвейер вообще нужен

Перед любой задачей агент оценивает масштаб:

- **S** (до ~30 мин, 1–3 файла) — делать сразу, одна строка в журнал. Конвейер не нужен.
- **M** (до полудня) — мини-план 5–10 строк в чате → «ок» человека → делать.
- **L** (больше дня / новый проект / внешние интеграции / деньги) — агент **обязан** предложить спек-режим одним вопросом. Молча начинать L-задачу запрещено.

Зачем: без порога агенты либо бюрократизируют мелочи, либо кидаются в большое без плана — и то и другое жжёт лимиты.

## 1. pf-spec — допрос до спецификации

Человек отвечает на вопросы **один раз в начале**, дальше агенты работают автономно.

- Один вопрос за раз; к каждому — рекомендуемый ответ агента с последствиями («я бы выбрал X, цена — …»).
- Факты из файлов/кода/сети агент ищет сам; человека спрашивает только о решениях (цели, границы, приоритеты).
- Выход — `SPEC.md`: проблема, что делаем, что НЕ делаем, допущения, критерии приёмки, риски, история изменений.
- Спека без «ок» человека — черновик, по ней не работают.

## 2. pf-tickets — нарезка на тикеты

- Каждый тикет **самодостаточен**: исполнитель увидит только тикет + правила проекта, не чат постановщика. Никаких «допиши здесь» (No Placeholders).
- Размер: тикет ≤ ~2 часов одной сессии. Зависимости — `depends_on`; статусы: `todo | in_progress | review | blocked | done | cancelled`.
- Каждому тикету — рекомендация: кто исполняет (какой агент) и класс модели (думать — старшая, механика — Sonnet-класс).
- **Шлюз параллельности**: если ≥5 тикетов взаимно независимы — агент предлагает выбор: очередь (дешевле) или параллельный запуск в несколько окон/субагентами (быстрее, но дороже по токенам). Решает человек.
- Файлы: `.agents/runtime/tasks/T-###-slug.md` (шаблон — в skills/pf-tickets/references/).

## 3. pf-do — исполнение тикета в свежем окне

Ключевая идея экономии: **новое окно чата на тикет**. Исполнитель читает только тикет + правила — контекст маленький, качество выше, лимиты целы.

Контракт исполнителя: взял → `in_progress` + owner; блокер → `blocked` + причина, не обходить молча; перед «готово» — свежий вывод команды-проверки по **каждому** критерию приёмки; заполнить «Результат» (что сделано, коммиты, отклонения, доказательства) → `review`. **Коммит(ы) на тикет обязательны**, хеши — в «Результат»; `done` ставит человек или ревьюер.

Запуск: новое окно → «выполни тикет T-003».

## 4. pf-replan — изменение курса без потери сделанного

Когда посреди работы меняется идея: не продолжать по инерции и не переделывать всё.

- Трассировка влияния по цепочке «спека → тикеты → коммиты»: какие разделы SPEC задеты → какие тикеты на них ссылаются → их зависимые.
- Класс влияния: **A** — аддитивное (дописать спеку + тикеты в хвост); **B** — меняет невыполненное (переписать/отменить todo-тикеты); **C** — инвалидирует сделанное (точечный `git revert` коммитов затронутых тикетов ИЛИ переделка поверх — оба варианта с ценой, рекомендуется дешёвый).
- Всё — только после «ок» человека; запись в «Историю изменений» спеки и в журнал.

## 5. pf-retro — пересмотр процессов

Раз в 2 недели (когда процесс устоялся — раз в месяц): сводка журналов и тикетов всех проектов → что буксовало, что повторяется руками ≥3 раз (кандидат на автоматизацию), что не используется (кандидат на отключение).

Шкала доверия автоматизаций: **L1** — только отчёт → **L2** — делает с подтверждением → **L3** — сам (только при наличии списка запретов, бюджета и стоп-крана). Повышение — после 2 чистых прогонов; инцидент — немедленное понижение.

## 6. Общая шина: файлы и журнал

- Тикеты, спеки, журнал — обычный Markdown в git. Любой CLI-агент это читает; человек — тоже.
- Журнал решений `.agents/journal/YYYY-MM-DD.md` (в git): `## HH:MM · агент · задача` + Что/Почему/Как/Итог/Коммит. Журнал — про «почему», git — про «что».
- Протокол старта сессии: правила проекта → журнал за 3 дня → тикеты со статусом ≠ done. Так любой агент знает, что делали другие.

## 7. Роли агентов

- **pf-architect** — ведёт допрос и нарезку; кода не пишет.
- **pf-executor** — исполняет ровно один тикет (Sonnet-класс: дёшево, по готовому плану).
- **pf-reviewer** — перепроверяет каждый критерий сам, «Результату» на слово не верит; вердикт `done` или возврат со списком 🔴/🟡/💭.

## 8. pf-auto — автопилот («сделай сам всё до конца»)

Включается **только** явной командой `/pf-auto` или фразой («сделай на автопилоте», «сделай сам всё до конца»); молча включать запрещено. Требует утверждённый SPEC и тикеты — допрос не автоматизируется, на вопросы отвечает человек. Дальше оркестратор доводит задачу до конца сам:

- Группирует тикеты в **задания по 1–3** (крупность ограничена окном исполнителя) и ведёт волны по зависимостям; параллельно ≤2 задания и только без общих файлов.
- Каждое задание исполняет **свежий субагент** по контракту pf-do: полный результат — в тикеты, оркестратору — сводка ≤15 строк (его окно бережётся для координации).
- **Гейт по риску** (`gate = auto`): после каждого задания там, где задания строят друг на друге или правят исполняемое (код, конфиги, схемы, скрипты); один гейт на веху — там, где задания независимы и правка дёшева (тексты, доки, отдельные страницы). Независимый субагент-ревьюер перепроверяет каждый критерий доказательствами по диффу; «Результату» исполнителя не верит. Всегда обязательны: гейт перед зависимым заданием, гейт перед внешним действием и финальный сквозной ревью.
- Замечания → **фикс-цикл ≤3 раундов**: 1–2 — тот же исполнитель, 3 — свежий на более сильной модели; после лимита — `blocked` и доклад человеку. Вечных циклов нет.
- **Стопы**: вопрос, решаемый только человеком; тикет противоречит спеке (мини-отчёт pf-replan); внешние необратимые действия (публикация на живой сайт, деплой, рассылки, DNS, деньги) — подготовить и спросить; пороги контекстного окна оркестратора.
- **Финал**: сквозной ревью всего результата по SPEC на самой сильной модели → один фикс-заход → done и отчёт человеку (сделано / доказательства / запаркованное / статистика волн и раундов).
- Реестр волн — в HANDOFF (если установлен компаньон pf-handoff) или в `.agents/runtime/autopilot-run.md`. Шаблоны промптов диспетчеризации — `skills/pf-auto/references/dispatch-templates.md`.

## 9. Непрерывность сессий — компаньон pf-handoff

Длинные сессии упираются в контекстное окно. Эту проблему решает отдельный инструмент [pf-handoff](https://github.com/turvodnik/pf-handoff): живая шпаргалка состояния задачи, датчик заполнения окна с порогами 60/80/90 %, выживание при сжатии истории (компакте) и подхват в новом чате (`/pf-resume`). pf-do и pf-replan рассчитаны на работу в связке с ним, но pf-workflow работоспособен и без него.
