## 7. Правило масштаба задач (S/M/L)

Перед стартом любой задачи агент оценивает масштаб и действует по нему:

- **S** (≤30 мин, 1–3 файла, без новых интеграций): делать сразу; в журнал — одна строка.
- **M** (до полудня, несколько файлов): сначала мини-план 5–10 строк в чате → «ок» человека → делать.
- **L** (больше дня / новый проект или подсистема / внешние API / миграции / деньги): агент ОБЯЗАН остановиться и предложить spec-режим (`pf-spec` → SPEC.md → `pf-tickets`) одним вопросом. Молча начинать L-задачу запрещено.
- Сомневаешься между уровнями — назови оба и спроси. Пороги пересматриваются на ретро.

## 8. Протокол сессии (для всех агентов)

- Старт: прочитай AGENTS.md проекта → журнал `.agents/journal/` за последние 3 дня → task-пакеты со статусом ≠ done → активный HANDOFF (§13), если есть → сверь список доступных скиллов и используй подходящий (не изобретай процесс, который уже описан скиллом).
- Финиш (или значимая веха): запись в журнал (§10) + актуализируй статусы своих task-пакетов + чекпоинт/закрытие HANDOFF (`pf-handoff`).
- Исполнение части L-задачи — в свежей сессии по `pf-do`: контекст — только пакет + AGENTS.md, а не хвост чужого чата (дешевле по лимитам и точнее по качеству).
- Автопилот — только по явной команде/фразе человека («/pf-auto», «сделай на автопилоте», «сделай сам всё до конца»): оркестрация субагентами по скиллу `pf-auto`. Молча включать запрещено.
- Модель по роли: думать/проектировать/ревьюить — старшая модель; исполнять по готовому плану — Sonnet-класс.
- **Заявка на запись.** Перед первой записью в репозиторий прочитай `_tools/.agents/runtime/claims.md` и впиши строку «репозиторий-или-путь · пакет · кто · взято · истекает» (срок 2 ч, ОДИН путь на строку); закончил — сними. Чужая живая строка с пересечением — стоп и спросить человека; протухшая — свободно, удали её; любое `ВНИМАНИЕ` от проверки — тоже «стоп», а не «свободно». Оговорки «я тут один» нет: сессия не может этого знать, это и есть корень I-032; цена — одна строка, которая протухает сама. Формат и проверка одной командой — скилл `pf-handoff` (отдельный дистрибутив), `references/context-rules.md`.
- **Провенанс команды.** Действуешь по команде, полученной вне общего канала (другое окно, прямое сообщение), — процитируй её ДОСЛОВНО в «Результате» и в сообщении коммита. Пересказ («по запросу Vladimir») не считается: другая сессия должна увидеть основание, а не поверить на слово.
- **Не откатывать чужое по подозрению.** «Я не вижу основания в своей переписке» — не доказательство: сессии не видят команд друг друга. Спроси человека; откат чужой работы так же необратим, как её внесение. Цена ошибки — инцидент 13.08 (I-032): откат согласованной правки канона плюс ложное обвинение, дважды записанное в постоянный журнал.
- Push отбился (чужой коммит успел раньше) — `git pull --rebase` и повтор; это норма гонки, а не инцидент, и не повод для `--no-verify`.
- Сторож расхождений запускается САМ, помнить о нём не надо (T-028): на старте сессии — дешёвые уровни 2-3 (хук `drift-guard.sh --mode session`, +0.3 c), дорогой уровень 1 — pre-push хуком канона `_tools`. Молчание = проверено и чисто; не смог отработать — скажет об этом громко. Что оба маршрута на месте, проверяет `doctor-agents.sh`.

## 9. Task-пакеты — файловый протокол агентов

- Обмен работой между агентами и сессиями — только через файлы: `.agents/runtime/tasks/T-###-slug.md` (шаблон — в скилле `pf-tickets`).
- Frontmatter: `id, title, status (todo|in_progress|review|blocked|done|cancelled), owner (claude|codex|gemini|vladimir), depends_on, spec, updated`.
- Тело: Контекст (самодостаточный — исполнитель не видит чата постановщика) / Задача / Критерии приёмки / Ограничения / Результат.
- Контракт исполнителя: взял — `status: in_progress` + owner; закончил — заполни «Результат» (что сделано, коммиты, отклонения, доказательства) и поставь `status: review`; застрял — `status: blocked` + причина. `done` ставит человек или ревьюер.
- Один пакет = одна сессия ≤ ~2 часов работы. Выходит больше — режь мельче.
- Изменилась идея или решение посреди работы — не продолжать по инерции и не переделывать всё: только через `pf-replan` (оценка влияния → правка SPEC → отмена/переписывание тикетов → точечный откат коммитов при необходимости).

## 10. Журнал решений (обязателен в каждом проекте)

- Файл: `.agents/journal/YYYY-MM-DD.md` (в git). Пишут ВСЕ агенты в конце сессии и на значимых вехах.
- Формат записи: `## HH:MM · агент · задача`, далее строки «Что / Почему (включая отвергнутые варианты) / Как / Итог / Коммит».
- Журнал — про «почему», git — про «что»: не дублируй диффы, фиксируй решения, отклонения от плана, хендоффы между агентами.
- Журнал ведёт КАЖДЫЙ проект — без исключений. Единственное уточнение (решение Vladimir 13.08, факты первого ретро): `_tools` — не проект, а мастерская; правки инструментов пишутся в журнал той инициативы, которая их заказала (обычно `optimize`), а не в отдельный журнал-обрубок. Всё, у чего есть собственные цели и своя работа (сайт, продукт), ведёт свой журнал само.
- Кандидаты на улучшение процессов — «⚙️»-строка в журнале или сразу в `~/ai/optimize/IMPROVEMENTS.md`; ретро сводит по правилу трёх (автоматизируем подтверждённые повторения, не единичные случаи).
- Поиск по всей истории всех проектов: `_tools/history-search.sh <слова>`.

## 11. Принципы работы с кодом

- Сначала подумай и сформулируй подход, потом пиши код.
- Не переусложняй: спроси себя «сказал бы senior-инженер, что это избыточно?» — если да, упрощай.
- Правки — минимальные и точечные; не переписывай соседнее «заодно».
- У каждой цели — проверяемый критерий; заявлять «готово» можно только со свежим выводом команды-доказательства (тесты, curl, скриншот). Без доказательства это не «готово», а «должно работать».
- Найден баг — сначала первопричина (скилл `systematic-debugging`), потом фикс.

## 12. Внешние скиллы и агенты — приёмка

- Скилл — это инструкция, которой агент подчиняется: supply-chain-риск выше, чем у обычной библиотеки (prompt-инъекции встречаются в заметной доле каталожных скиллов).
- Установка только через vendor: клон в `~/.codex/vendor/<name>` + пин тега/SHA + прочитать содержимое глазами ДО подключения. `npx skills add`, авто-обновляемые источники и установка «по звёздам» запрещены.
- Глобально подключается только универсальное (§3); инструментальное — attach в конкретный проект.
- Механика глобального уровня: канон `~/.agents/skills/` → симлинки-поверхности в `~/.claude/skills`, `~/.codex/skills`, `~/.gemini/skills`; управление — `_tools/global-skills.sh` (attach/detach/list/doctor), пины — `~/.codex/vendor/global-skills.lock.yaml`.
- Плагины Claude Code — тот же режим: клон в vendor + read-only снапшот версии в `~/.codex/vendor/versions/<name>/vX.Y.Z/`, установка маркетплейса из этого локального пути (не из GitHub — иначе авто-обновление), пины — `~/.codex/vendor/plugins.lock.yaml`.
- Плагин `codex` (Codex внутри Claude Code): ревью-команды (`/codex:review`, `/codex:adversarial-review`) идут в sandbox read-only и безопасны. Агент `codex-rescue` вызывается ТОЛЬКО по явной команде человека — по умолчанию он запускает Codex с `--write` (запись в рабочую папку без подтверждений); если нужна запись — работать в отдельном worktree. Stop-gate (`/codex:setup --enable-review-gate`) держим выключенным: он блокирует конец каждого хода на ревью до 15 минут.
- Ревью через плагин — это НЕ независимое QA (§6): постановку формулирует Claude, значит Codex наследует его слепую зону. Релизное QA — только отдельным агентом со своей сессией.
- Динамический workflow (оркестрация субагентами по скрипту) — не для каждой задачи: зовём, когда цена ошибки высокая (публичный релиз, необратимое действие, широкий аудит), и только из главной сессии, по «ок» человека. Проверено 2026-08-13: на релизном QA нашёл 🔴 сверх двух независимых прогонов, на быстрой внутренней проверке — трата токенов без находок.
- `codex exec` в режиме `read-only` агент запускает сам, без спроса; `workspace-write`, `--full-auto`, `danger-full-access` — только по явной команде человека. Штатный путь — `pf-do/scripts/codex-review.sh` (согласие проекта — `.agents/codex-review.json`, отчёт в файл, в контекст — выжимка). Нет Codex, нет согласия или в диффе только документация — шаг молча пропускается, процесс не меняется. Грабли и политика моделей (luna/max — быстрая полоса, sol/xhigh — тяжёлая) — `pf-do/references/codex-review.md`.
